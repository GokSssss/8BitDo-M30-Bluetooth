# Обновление M30 Bluetooth с Android — 26 октября 2026

Техническая основа есть: Android USB Host позволяет приложению работать с USB-интерфейсами и конечными точками. Поддержка зависит от телефона и кабеля. Официальный Upgrade Tool 8BitDo на странице производителя предлагается для Windows и macOS; подтверждённой официальной Android-утилиты для M30 не найдено.

Источники:
- https://developer.android.com/develop/connectivity/usb/host
- https://support.8bitdo.com/firmware-updater.html

В fwupd есть открытый плагин ebitdo и явное описание M30 2DC8:5006. Загрузчик 2DC8:5750 общий для нескольких моделей, поэтому одного VID/PID недостаточно для разрешения записи прошивки. В плагине указаны разные USB endpoints для обычного режима и загрузчика. Это подтверждает возможность переноса обмена на Android, но не является проверкой телефона или данного экземпляра M30.

Источники:
- https://github.com/fwupd/fwupd/blob/main/plugins/ebitdo/README.md
- https://github.com/fwupd/fwupd/blob/main/plugins/ebitdo/ebitdo.quirk
- https://github.com/fwupd/fwupd/blob/main/plugins/ebitdo/fu-ebitdo-device.c

У новых DAT для M30 несколько последовательно упакованных секций. Поддержка этого формата добавлена в fwupd PR #9711; в обсуждении есть результаты аппаратной проверки и проблема финального ACK при переподключении. Значит, реализация должна проверять весь пакет, обрабатывать исчезновение устройства и не объявлять успех по одной отправленной секции. Исходники fwupd имеют LGPL-2.1-or-later; их перенос требует соблюдения лицензии. В текущую сборку код протокола fwupd не копировался.

Источники:
- https://github.com/fwupd/fwupd/pull/9711
- https://github.com/fwupd/fwupd/blob/main/plugins/ebitdo/fu-ebitdo-firmware.c

## Что сделано в Companion 1.13

Добавлен просмотр USB-дескрипторов. Он не открывает соединение, не захватывает интерфейсы и не отправляет команды устройству. Это позволяет проверить, обнаруживает ли телефон M30 в обычном режиме и загрузчик. USB bcdDevice явно отделён от версии прошивки. Кнопки «Обновить прошивку» нет: запись не реализована.

## Что остаётся для полноценного обновления

1. Получить USB-отчёт физического M30 с Android в обычном режиме и загрузчике; подтвердить доступ к HID endpoints после системного разрешения USB.
2. Реализовать и проверить запрос версии без переключения режима и записи.
3. Проверять официальный файл именно M30 Bluetooth, все секции, размер и целостность; исключить M30 2.4G и M30 Xbox.
4. Перенести обмен и подтверждения загрузчика, прогресс, таймауты, поведение при отключении и повторном обнаружении. Не запускать стирание или запись автоматически при подключении кабеля.
5. Провести запись и восстановление на тестовом контроллере. Доступа к физическому M30 из этой среды нет; на текущей стадии заявлять готовую прошивку с телефона нельзя.

## Физический отчёт 26 октября: загрузчик 3208

Пользователь подтвердил Windows/X-input USB 045E:028E, затем 8BitDo Boot 2DC8:3208, interface 0 HID class 3, interrupt endpoints IN81/OUT02, по 64 байта, bcdDevice 2.00. Это не профиль старого загрузчика 5750: IN82/OUT01 из fwupd. Версия прошивки из bcdDevice не выводится.

Для 3208 найдена открытая реализация Ultimate Bluetooth (не M30): https://github.com/alphaorderly/ultimate-bluetooth-updater/blob/main/ultimate_updater/protocol.py . Там команда 8 запрашивает 4-байтовый код модели, ответ содержит статус, адрес, длину и CRC16. В Companion 1.22 добавлен только такой экспериментальный запрос модели с проверкой ответа; в отличие от оригинала ответ не принудительно сравнивается с Ultimate PID 6007. Наличие общего ID не подтверждает модель или полную совместимость протокола.

Запрос запускается пользователем через «Кнопки → Дополнительно → Загрузчик · запрос модели», с разрешением Android USB. Выбирается единственный загрузчик 3208, интерфейс HID с точными endpoint/размером. Используются UsbRequest, таймауты, обязательный release/close; UI не блокируется. Иных команд и прошивки в запросе нет. Требуется аппаратный результат. Лицензия исходника MIT сохранена в THIRD-PARTY-NOTICES.txt.

Исходный код официального обновлятора не получен; официальная программа не декомпилировалась и её USB-обмен не записывался. Механика определяется по пользовательскому отчёту и открытым источникам. Для полноценной записи M30 нужно подтвердить совместимость на конкретной модели, официальный формат/образ, команды и завершение.

## Подтверждённый ответ модели и официальный DAT

Пользователь прислал физический ответ Companion 1.23: команда 8, статус 0, 64 байта, payload 06 50 00 00, CRC 0xBD00. Код модели 0x5006 соответствует M30 по fwupd. Запись по одному совпавшему model ID не разрешается автоматически. Версия приложения остаётся 1.23, новой аппаратно непроверенной прошивки или APK с записью нет.

## 1.25: официальные источники и чтение версии

Получены с сайта производителя: официальный Windows ZIP по ссылке https://download.8bitdo.com/Tools/FirmwareUpdater/8BitDo_Firmware_Updater_Win.zip и frontend https://web.8bitdo.com/ . Windows DLL скачана, но не декомпилировалась и на контроллере не запускалась. Для анализа протокола использован официальный frontend /assets/index-BXAl9J5z.js и /assets/connectDevice-CqNxlsyD.js. Проприетарные файлы не включены в исходники/поставку Companion.

В официальной таблице M30: PID 20486 (5006), firmware type 23, model 80HA. Для этого PID официальный Tt выбирает De, которая через Ie читает 4 байта из OH: 0x01000000+98304-4096+32+32 = 0x01017040. Команда чтения Ge/GH = 194 (0xC2), не команда 1 из неофициального клиента Ultimate. Для M30 нет попадания в специальные списки пропуска/чтения версии 0x20/0xC0. Главное поле версии читается UInt16 LE, интерфейс делит его на 100: 201 означает 2.01. Дополнительные байты не интерпретируются как beta без аппаратного подтверждения.

В Companion реализован собственный код только формата этого запроса: 64 байта, packet[0]=5, cmd LE at1=C2, len at5=4, crc at7=0, total at9=4, address at13=01017040. Ответ: 00 05, status at2=0, cmd at4=C2, len at6=4, crc at8, total at10=4, address at14=01017040, data at18..21; проверяется CRC16. В отличие от веб-клиента поля и целостность проверяются строго, а ошибка чтения версии сохраняет уже подтверждённую модель в отчёте. Сначала обязательно команда 8 и модель 5006. Другим моделям C2 не отправляется.

Новая API каталога официального веб-обновлятора: POST https://support.8bitdo.com/restapi/link/v1/client/firmware/select с JSON {firmware_type:23,beta:0}. Для 2.01 возвращает HTTPS DAT https://support.8bitdo.com/bd-uploads/files/old/9bf8ddad-4f37-4297-9fa1-f48a48c5dbc6.dat . Получены те же 151608 байт, SHA256 158c4b39757048204eba76cd94e33faf087408a6ad79f027b6253ab0a69d5287, MD5 280a10c75a240bbe132c74ae2e921cc1, тогда как новый каталог также хранит 424780ACCB0317D8CB9AAA6128C50DE2. Для 2.00 фактический MD5 7861ff592632f0d56bb1288a756d5ec8 также отличается от каталожного D391953371F52DF0A333188FAE8A265D. Старая и новая загрузки 2.01 совпадают побайтно, причина каталожного MD5 всё ещё не установлена. Официальный frontend в изученном q проверяет размер, но этот факт не принят как разрешение игнорировать расхождение в Companion.

Интерфейс 1.25: внутри «Прошивка · проверка USB» кнопка «Считать модель и версию M30». Результат версии пока не привязывается к Bluetooth-дескриптору и не подменяет FW в шапке для другого контроллера. Чтение C2 требует физического результата, прошивка не записывается.

## 1.28: перенос механизма официальной Windows-утилиты в APK

Цель — установка неизменённых официальных обновлений; переназначение кнопок и изменение образа не реализуются.

Выполнен статический анализ скачанной 8BitDoFirmwareUpdaterTools.dll посредством objdump и Ghidra 11.0.3. Vendor DLL и результаты декомпиляции хранятся только в scratch, не входят в исходники или APK. Формат команд независимо реализован на Java. Программа Windows не выполнялась и USB-трасса её работы не записывалась. Ниже — выводы анализа кода, ещё не аппаратная проверка.

### Исправление прежнего предположения о двух секциях

Для загрузчика 3208 и model 0x5006 официальный Windows-код выбирает секцию DAT с PID 0x5006. Предыдущее предположение, что на этом пути обязательно записывать обе секции подряд, неверно. Ветви дополнительной записи PID 0 относятся к другим моделям. APK сохраняет целиком исходный DAT, проверяет оба заголовка, но на этом пути пишет только выбранный payload 0x5006; PID 0 не стирает и не записывает.

Ориентиры для воспроизводимости в DLL (image base 0x10000000):
- FUN_1000bd20 — основной путь BOOT, запрос модели и запуск записи.
- FUN_10007750, сравнение 0x5006 около 0x100079AB и FUN_10007050 — выбор секции по PID.
- FUN_1000d240 включает 0x5006 в группу с CRC16 запросов.
- FUN_100091c0 — построение пакета: байт 05, command LE16, params LE16, length LE16, CRC16, total LE32, address LE32, payload с offset 17, до 46 байт. CRC пустого фактического payload = FFFF.
- FUN_10009290 — чтение памяти командой 5. Для чтения версии APK теперь использует её и адрес 0x01017040. Ранее реализованная C2 была найдена в web-клиенте; аппаратный ответ C2 по-прежнему не получен.
- FUN_10009e70 — стирание командой 4.
- FUN_1000a040 — command 3 для encrypted payload и command 2 для обычной записи.
- FUN_1000a0e0 — reset command 7.

Последовательность для M30:
1. Запрос модели 8 (формат, уже подтверждённый на физическом M30) и проверка 5006.
2. Чтение версии command 5, length=4, total=4, address=01017040, CRC пустого исходящего payload FFFF. Проверка размера, статуса, команды, адреса и CRC ответа.
3. Erase command 4: адрес выбранной секции (01018000), total=её длина; затем erase 01017040/32.
4. Command 3: исходные зашифрованные байты секции блоками до 46 байт, непрерывные адреса, total=полная длина секции, CRC16 каждого payload. APK не расшифровывает и не меняет эти данные.
5. Повторный erase 01017040/32, затем command 2: четыре исходных байта version из заголовка по 01017040.
6. Добавленная собственная проверка — повторное чтение этой версии command 5; при несовпадении reset не отправляется.
7. Reset command 7; после него APK ждёт исчезновения исходного BOOT и появления M30 runtime по USB. Без этого 100%/успех не объявляются. Ответы encrypted-write подтверждают загрузку блоков, но не являются независимым полным чтением flash назад.

Ожидание ACK ограничено; при ошибке или отключении APK прекращает операцию, без автоматического повторного стирания и reset после ошибки. Работа идёт в foreground connectedDevice service с wake lock, а не привязана к существованию Activity. Неизвестная модель, версия или файл не допускаются к стиранию; понижение версии отключено. Opening screen/file selection/USB attachment не запускают запись. Пользователь отдельно подтверждает установку.

### Проверка официального файла и расхождение MD5

Повторно запрошены официальный HTTPS-каталог type 23 и файл 2.01 с support.8bitdo.com. Размер и SHA-256 совпали с прежними загрузками; MD5 каталога по-прежнему отличается. Простое исключение заголовков/отдельные секции расхождение не объясняют. Причина не установлена, файл не называется подписанным или совпавшим с каталожным MD5.

В 1.28 допуск реализован по отдельному списку точных SHA-256 неизменённых файлов, полученных с официального HTTPS-сервера, вместе с версией, размером, PID и адресами. Это осознанное изменение прежнего решения полностью блокировать пакет по расхождению каталожного MD5. Отсутствие совпадения MD5 не скрывается: явно показано в экране файла, подтверждении установки и отчёте. SHA-256 pins удостоверяют соответствие наблюдавшимся HTTPS-байтам, не заменяют цифровую подпись производителя.

Допущенные файлы:
- 2.01, 151608 байт, SHA256 158c4b39757048204eba76cd94e33faf087408a6ad79f027b6253ab0a69d5287, URL https://support.8bitdo.com/bd-uploads/files/old/9bf8ddad-4f37-4297-9fa1-f48a48c5dbc6.dat .
- 2.00, 149560 байт, SHA256 46c06f9ef51f11833bc7d94aab917e061273c16cc5ffabdc364acc11f512bde9, URL https://support.8bitdo.com/bd-uploads/files/old/0d6ccc95-a085-4978-aea6-c7641b88fb93.dat .

Прошивки не распространяются внутри APK/ZIP/Drive. Кнопка загрузки открывает официальный HTTPS URL в браузере, затем пользователь выбирает DAT через системный проводник. Разрешение INTERNET приложению не добавлялось.

### Проверки и предел готовности

13 core-наборов, включая строгий парсер DAT и симулятор обмена. Полный прогон механизма на реальных байтах официальных файлов 2.01 и 2.00 с искусственными USB-ответами: байты выбранной секции совпадают, PID 0 не записан, порядок команд и последняя короткая посылка корректны, нераспознанный файл/другая модель/понижение/обрыв/плохой ACK/CRC/ошибка readback останавливают операцию. В 1.30 добавлены явное зелёное подтверждение, сохранённая версия/тип результата и перенос старого отчёта только при точном формате финального успеха. Выбор/чтение файла не считаются установкой. При новом чтении равной версии показано отдельное подтверждение текущей версии и заблокирована ненужная повторная запись.
